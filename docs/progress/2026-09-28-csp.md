# A real Content-Security-Policy, live-tested against Razorpay, OneSignal, and Sentry

The last session's overnight security pass deliberately left one thing undone: a Content-Security-Policy.
The reasoning at the time was sound — this app loads a real payment SDK, a push SDK, and an error
reporter, and a CSP written without testing each of those live is exactly the kind of change that can
silently break checkout days later. This session did that live test.

## The approach: nonce + `strict-dynamic`, not a host allowlist

A plain host-allowlist CSP (`script-src 'self' https://checkout.razorpay.com https://cdn.onesignal.com …`)
is the easy version, but it's also the weaker one — anything on that list becomes a place an attacker's
injected script could hide, and it gets stale as vendors add subdomains (Razorpay's checkout.js turned out
to dynamically load a *second* script, `cdn.razorpay.com/static/cx/razorpay-risk-detection/bundle.js`, that
wouldn't have been on anyone's guessed list). Next.js's own current guidance
(`nextjs.org/docs/app/guides/content-security-policy`) is a per-request nonce combined with
`'strict-dynamic'`: a script tagged with the nonce is trusted, and — this is the mechanism that matters
here — anything *that trusted script* goes on to load dynamically (via `document.createElement('script')`
or another `next/script`) inherits that trust automatically, recursively, regardless of its URL. That's
precisely the shape of both integrations: `components/shop/PayNowButton.tsx` builds the Razorpay
`<script>` tag itself in a click handler, and OneSignal's own SDK does its config fetch as a dynamically
inserted script. Neither needs to be named in `script-src` at all — the nonce on the *initiating* code is
enough, and it's a strictly stronger guarantee than a host allowlist. `frame-src`, `connect-src` etc. are
unaffected by `strict-dynamic` and still need real entries, which is what this session verified live.

This only works because the whole app was already forced into dynamic rendering (the root layout calls
`getServerUser()`/`headers()` on every request) — nonces require a fresh value per request, which is
incompatible with static generation. Confirmed via `next build`: every route was already `ƒ` (dynamic)
before this change and still is after — no rendering-mode regression to worry about.

**What changed**, all in [`proxy.ts`](../../proxy.ts) (Next 16's renamed `middleware.ts` — this is where
Next's docs say the nonce must be minted, once per request):
- A `buildCsp(nonce)` helper assembles the policy; `img-src`/`connect-src` pull the Supabase Storage host
  from `NEXT_PUBLIC_SUPABASE_URL` and the Sentry ingest host from `NEXT_PUBLIC_SENTRY_DSN` at runtime
  rather than being hand-typed, so they can't drift from the real configured values.
- Every return path (the normal pass-through *and* all three auth-redirect branches) now sets the header
  and carries the nonce — previously only the pass-through response existed as a named variable, and the
  redirect branches returned bare `NextResponse.redirect()`s. Fixing this uncovered a small pre-existing
  bug worth noting: those redirects also weren't carrying over session-refresh cookies set earlier in the
  same request (`response.cookies` via Supabase's `setAll`), so a token refresh that happened to land on a
  request that also redirected would have been silently dropped, self-healing on the next request. Now
  fixed as a side effect of restructuring this function for the CSP work.
- [`app/layout.tsx`](../../app/layout.tsx) reads the nonce back out via `headers().get("x-nonce")` (Next
  auto-applies it to its own framework/page bundles; a third-party `next/script` needs it passed
  explicitly) and hands it to `OneSignalIdentity`, which now takes an optional `nonce` prop.

`style-src` deliberately allows `'unsafe-inline'` rather than going nonce-strict there too: ~40 components
set dynamic `style={{}}` values (percentages, hues, computed sizes — all from server data or theme tokens,
never raw user text; checked every one) and Safari doesn't support `style-src-attr` (the finer-grained
alternative that would let a strict `style-src` coexist with inline style *attributes*), so a strict
`style-src` would just silently misrender the whole site in one major browser for no real XSS benefit here.

## Live-tested, not guessed — what was actually exercised against the running dev server

Signed in as the real test accounts and drove the app through the browser, watching the console and the
Performance API's resource-timing entries (a CSP-blocked request never gets an entry there at all, which
is a more reliable signal than network-request logs for some request types this session's tooling didn't
capture consistently, e.g. cross-origin iframe loads and plain `<img>` loads):

- **Homepage, sign-in, sign-up, diary, orders, admin, a real product page** — all rendered correctly, zero
  CSP console violations, across both anonymous and three different signed-in roles.
- **Razorpay, for real**: clicked "Pay" on a genuine unpaid draft order and confirmed via direct DOM/JS
  introspection that `checkout.razorpay.com/v1/checkout.js` loaded, that it went on to dynamically load
  `cdn.razorpay.com/static/cx/razorpay-risk-detection/bundle.js` (not something anyone would have thought
  to allowlist by hand — exactly the case `strict-dynamic` exists for), that `window.Razorpay` initialized,
  and that the real payment iframe (`https://api.razorpay.com/v1/checkout/public?...`, Test Mode ribbon and
  all) rendered — meaning the explicit `frame-src` entry for it is correct. Didn't complete the payment
  itself, same reasoning as last session: that iframe is a real cross-origin surface this session's browser
  tool can't see into, so there's no way to interact with it that isn't blind guessing at a live payment
  UI.
- **Supabase Storage `img-src`**: no diary contact in the seed data has an uploaded photo (the file-picker
  limitation from last session is unchanged), so instead of leaving this unverified, injected a real
  `<img>` pointing at the actual configured Supabase Storage host directly and confirmed via
  `performance.getEntriesByType("resource")` that the browser attempted the network request (a 404 for the
  fake filename, but a 404 is a network outcome — a CSP block never reaches the network at all, and
  produces its own distinct console message, which did not appear).
- **OneSignal's SDK script itself**: loads for signed-in users only, and is gated off on `localhost` in
  `app/layout.tsx` — a pre-existing guard, unrelated to this session, because the SDK independently refuses
  to run anywhere but the origin configured in its own dashboard. Temporarily forced that gate open purely
  to observe the SDK's CSP-relevant behavior, confirmed the nonce'd `next/script` tag loaded the real
  `cdn.onesignal.com` bundle with **zero CSP violations**, watched it fail on its own unrelated
  origin-lock check (`"Error: Can only be used on: https://giftping-lime.vercel.app"` — its error, not
  CSP's), then reverted the gate immediately. **Genuinely unverified**: the SDK's downstream behavior
  (its config fetch to `api.onesignal.com`, its websocket) never ran locally because of that origin lock —
  the `connect-src` entries for it are informed by OneSignal's own CSP guidance, not confirmed against a
  real network call. This needs one real check on the actual production domain after deploy, where the
  dashboard's configured origin will actually match.
- **Sentry's `connect-src`**: `instrumentation-client.ts` has `enabled: process.env.NODE_ENV === "production"`
  — it never fires a network call in dev regardless of CSP, so this couldn't be exercised live either. The
  host in the policy is parsed directly from the real `NEXT_PUBLIC_SENTRY_DSN` value at runtime rather than
  typed by hand, which is about as high-confidence as an unexercised entry can be, but it's still not the
  same as watching a real event land.
- **Full regression**: `tsc --noEmit` clean, `npx vitest run` — 291/291 passing, `npx eslint .` clean,
  `next build` clean with every route still dynamically rendered (no static/ISR regression from the nonce
  requirement).

## What's still open

Two directives (OneSignal's runtime `connect-src`, Sentry's `connect-src`) are correct by research and
configuration-derivation but not by a live-observed network call, for the reasons above — both need one
real confirmation after the next production deploy: subscribe to push for real on the live domain, and
trigger one real Sentry-reported error, and check neither is silently blocked. Everything else in this
policy — every script-loading path, the one real third-party iframe, and the one real cross-origin image
host — was watched working, not assumed.
