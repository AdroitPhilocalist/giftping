# Stage 12 (slice 15) — the diary blocked page scroll, and local sign-in was silently landing on production

Two reports from the developer after the flip-book slices: (1) hovering the mouse anywhere over the diary and scrolling did nothing — the page above/below the book couldn't be reached; (2) confusion about whether to test against `localhost` or the Vercel deployment, with account data appearing to leak between accounts when testing on `localhost`.

## 1. The diary silently ate every mouse-wheel scroll over it

**Cause**: `DiaryBook`'s outer element keeps the `dy-book--fit` class (for its height-clamp rule, reused from the older two-page `Book`), so a spread page also matched the *older* `.dy-book--fit .dy-page-scroll` rule from before the flip book existed — which sets `overflow-y: auto` and, deliberately for that older component, `overscroll-behavior: contain` (so its own internal scroll doesn't chain into the page behind it). The newer flip-specific rule (`.dy-stage .dy-page-scroll { overflow: hidden; ... }`) overrides `overflow-y` back to `hidden` for the flip book (correct — `FitPage` means a spread page never actually scrolls internally), but never touched `overscroll-behavior`, so `contain` was left standing from the older rule. A `contain`ed, non-scrolling element still swallows wheel input in Chromium instead of letting it chain to the page underneath — so a page that can't scroll blocked *everything* above and below it from scrolling too, exactly where the diary sits.

**Fix**: one rule, `.dy-stage[data-mode="spread"] .dy-page-scroll { overscroll-behavior: auto; }`, right beside the existing per-mode overrides. Single-page mode (tablet/phone) keeps `overscroll-behavior: contain` — that one is real: those pages do scroll inside themselves, and containing that scroll is correct there.

**Verified**: at 1280×720, 1440×780 and 1440×900, a wheel-scroll dispatched at the exact centre of the book now moves `window.scrollY` (previously stuck at 0 no matter how much was scrolled); a wheel-scroll over the header still worked before the fix, confirming the block was specific to the book. Single mode (1024×768) still reports `overscroll-behavior: contain` unchanged.

## 2. `localhost` sign-in was landing on the production deployment

**Symptom, as described**: sign in on `localhost`, get redirected to `giftping-lime.vercel.app` after the sign-in flow completes; a person added to the diary under one account later "showed up" after signing in as a different account — but only when testing via `localhost`.

**Root cause**: `.env.local` — the file `npm run dev` loads — sets `NEXT_PUBLIC_APP_URL=https://giftping-lime.vercel.app` (so the same file also works for a `vercel env pull`). `lib/auth/actions.ts`'s `getAppUrl()` checked that variable *first*, unconditionally, before ever looking at the request's own origin. Google OAuth (`signInWithGoogleAction`), the sign-up confirmation email, and the password-reset email all build their callback URL from `getAppUrl()` — so on `localhost`, all three sent the browser to `https://giftping-lime.vercel.app/auth/callback` instead of back to `localhost:3000`. The OAuth session then gets established on the **production origin's cookies**, not `localhost`'s — so the `localhost` tab's own cookie never changes. Reopening `localhost` afterwards (even after restarting `npm run dev`, which doesn't matter — cookies live in the browser, not the server) still carries whichever account was last actually signed in *on that origin*, which can look exactly like "account A's data appearing under account B" if the developer believed the second sign-in had switched the `localhost` session and it never actually had.

This was **not** a data-isolation bug — it never crossed accounts inside the database. `diary_contacts` (and everything else) is still owner-scoped by RLS with no admin bypass, exactly as documented. It only ever looked that way because the browser tab believed it was signed in as someone it wasn't.

**Fix**: `getAppUrl()` now checks the request's own `Origin` header first (present on every browser-initiated Server Action call) and falls back to `NEXT_PUBLIC_APP_URL`, then `http://localhost:3000`, only when that header is absent. `localhost` now always redirects back to `localhost`; a real deployment always redirects back to itself. This also fixes a second, latent bug the same code would have hit on a Vercel **preview** deployment (a pull request build): those get their own unique `*.vercel.app` URL, and the old code would have bounced every preview's sign-in to the fixed production URL too.

**Which one to test against, going forward**: use `localhost` for anything not yet pushed — the Vercel deployment only ever serves the last pushed commit, so it cannot show local, uncommitted work. Both `localhost` and the deployment read and write the **same** Supabase database (there is no separate local database), so data an account creates on one is immediately visible to that same account on the other — that part was always correct and is not something to route around. If cross-account data ever appears again after this fix, that would be a real RLS regression worth flagging immediately, not a redirect confusion — the two look identical from the outside, which is what made this one worth chasing down properly rather than guessing.

## Not verified

The real Google OAuth flow end-to-end on `localhost` with the fix in place (no Google client available in this environment) — only the redirect URL construction (`getAppUrl()`'s new priority) and the callback route's own use of the request's real origin (already correct, unchanged) were checked directly.
