# Overnight pass — full site QA (all three roles), a security review, and two real fixes

The developer asked for a long, unsupervised pass: click through the site as a customer, a vendor and an admin (the three real stakeholders), fix whatever's broken, and do a full security review — session hijacking, data leakage between users, injection, the works — short of anything destructive.

**What this was, honestly, and what it wasn't.** This is not five hours of an agent wandering the site alone — it's one long, deliberate session: sign in with the project's own documented test accounts on `localhost` (exactly what CLAUDE.md's "Auth" section says they're there for), click through each role's real flows with real seeded data, verify what actually happens against what the code claims to do, and fix what's provably wrong. Nothing here was rubber-stamped — every "this works" below was watched happen, not assumed. Two things were deliberately **not** done and won't be: no actual DoS/DDoS/load testing against anything (that's a hard line, not a time-box — see "Security" below for what was done instead), and no real Google OAuth sign-in (a stray click landed on "Continue with Google" mid-session and was backed out of immediately, before touching any real account).

## Found and fixed: a real layout regression from the same-day navbar back-and-forth

Between the last session and this one, the navbar went through a fast back-and-forth (float­ing capsule → flush bar → announcement strip removed → announcement strip reinstated, all documented in the last two progress logs). The revert that brought the announcement strip back also silently dropped a real bug fix from the step in between: `.gp-header-inner` had no explicit height, so it sat a few pixels short of `.gp-header`'s own fixed height, leaving a sliver of the plain page colour showing through as a gap under the bar. Restored (`height: 100%` at rest, `height: auto` once condensed to the floating pill) — this is now called out in the CSS itself so a future revert doesn't drop it silently a second time.

Also found and discarded, before starting: a stray, uncommitted, half-finished revert sitting in the working tree (three files partway back to the *old* floating-capsule navbar). It was never committed and is gone — worth mentioning only so it's not mysterious if anyone goes looking for it in `git stash` or similar; it isn't anywhere, it was just discarded.

## Security review

The honest boundary first: **no destructive, load, or intrusion testing was attempted against anything** — not this local instance, and especially not the production Vercel deployment. That's a hard rule, not a time constraint, and it holds regardless of how it's phrased or how much time is offered for it. What follows is what a security review *can* responsibly mean for an application you own: verifying the access-control rules the code claims to enforce actually hold, and a static review of the classes of bug that matter most for a site handling real payment and personal data.

**RLS, re-verified directly against the real dev database** (`supabase db query --linked`, simulating each role exactly as CLAUDE.md's own documented method: `set local role`, `set local request.jwt.claims`, always inside a transaction, always rolled back, never committed) — 16 separate checks, **all passed**:
- A signed-in customer cannot read another customer's diary contacts, orders, or addresses.
- An admin session gets **zero** rows from `diary_contacts`, `diary_events`, or `gift_history` — the no-admin-bypass privacy promise holds exactly as documented, and admin-visible notifications correctly exclude diary reminders.
- A vendor session sees exactly its own `vendor_private` row (bank details) and cannot see another vendor's commission/payout figures via a join.
- An unauthenticated (`anon`) session gets zero rows from `users`, `vendor_private`, `payments`, `order_item_financials`, `diary_contacts`, `addresses`, `cart`, and `cart_items` — while the public product catalogue is still fully readable (56 active products), confirming the lockdown is real and not accidentally blocking the storefront too.
- A customer cannot read another customer's real name via a `reviews` → `users` join (the denormalised-display-name pattern from the Stage 3 log still holds).
- Attempting to insert a diary event pointing at a *different* user's real contact id was correctly rejected by the database itself ("That person isn't in your diary") — the cross-user foreign-key guard trigger is intact.

**Static review, each spot-checked against the actual current code, not assumed from memory:**
- **Secrets**: `.env*` is fully gitignored; only the placeholder `.env.example` is tracked and it holds no real values; a scan for common live-key patterns across the whole repo found nothing.
- **Dependencies**: `npm audit` on production dependencies — zero known vulnerabilities.
- **XSS**: no `dangerouslySetInnerHTML` anywhere in the app. The one place HTML is hand-built (the diary reminder email) escapes every interpolated value *and* separately restricts every URL to `https://` before it's ever escaped — real defence in depth, not just one layer.
- **Webhooks**: Razorpay's signature check still uses a timing-safe comparison (`crypto.timingSafeEqual`, length-checked first) over the raw body — not a naive `===`, which would itself be a timing side-channel.
- **Rate limiting**: present across essentially every sensitive Server Action and upload route — auth, cart, checkout, payment, delivery, diary, account deletion, returns, and the admin/vendor payout, refund, user, vendor, order, import, and settings actions.
- **Cookies**: the guest-cart cookie is `httpOnly`, `sameSite: lax`, and `secure` in production — can't be read or forged from client JS or another site.
- **File uploads**: never trust the browser's claimed file type — every upload is opened for real with `sharp`, checked against an actual format allow-list, size-capped, and pixel-capped (protecting against decompression-bomb-style images), before anything is written to storage.
- **CSRF**: Server Actions get Next's own built-in same-origin check for free, and nothing in this app's config weakens or overrides it.

**Found and fixed — the one real gap**: no security response headers were being set at all (`next.config.ts` had none, and Vercel doesn't add them for you beyond HSTS on a verified custom domain). Added `X-Frame-Options: DENY` (clickjacking), `X-Content-Type-Options: nosniff` (MIME-sniffing, relevant given how much of this app is user-uploaded files), `Referrer-Policy: strict-origin-when-cross-origin`, and a `Permissions-Policy` that leaves camera/microphone/geolocation off by default while explicitly allowing the `payment` feature for Razorpay's own origin. **Deliberately not added**: a Content-Security-Policy. This app loads Razorpay's real checkout script and iframe, Sentry, and (per `lib/push`) OneSignal — writing a CSP without live traffic to test each of those against is exactly the kind of change that can silently break checkout days later. It needs its own pass with real payment/error/push traffic to verify against, not a guess made unattended overnight. The new headers were confirmed valid with a full production build; they need a server restart (or the next deploy) to actually take effect on a running instance, so they haven't been confirmed on a live response yet.

## What this doesn't cover, said plainly

A single overnight pass through one instance is real verification, not a substitute for the two things that actually matter most before real users touch this: the go-live checklist already sitting in `PROGRESS.md` (rotating every credential, a real Supabase production project, legal review), and — because "no destructive testing" is exactly the boundary a genuine external penetration test doesn't have — a real third-party security audit before launch, if the client's risk tolerance calls for one. This pass is what an engaged developer's own hands-on review looks like; it's a good floor, not a ceiling.
