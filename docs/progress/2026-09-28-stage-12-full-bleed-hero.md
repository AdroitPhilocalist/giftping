# Stage 12 (slice 17) — the homepage hero runs full-width, and the header/announcement strip stop looking like two bars

The developer sent the client's actual approved homepage mockup (desktop + mobile side by side). Two things it made explicit that weren't yet true here: the atrium photo runs the **entire width** of the page with the headline sitting directly on top of it, not confined to the right 70% with the headline beside it on the plain cream page; and the announcement strip above the header reads as part of the same panel, not a second, slightly-different-toned bar stacked on it.

## The hero (`components/home/HomeHero.tsx`)

The image now fills the whole hero `<section>` (`absolute inset-0`, `object-cover`), and the headline/subcopy/buttons sit directly on top of it in a `relative` block above the image, in cream text (`text-brand-on-primary`) instead of the page's usual ink. A new `.gp-hero-scrim` class (`app/globals.css`) — a diagonal wash from the already-defined-but-previously-unused `--gp-hero-scrim` token, fading out by mid-image, plus a low horizontal one so the floating search card below still lands on what reads as solid ground — keeps the text legible over whatever happens to be in that part of the photo. A phone crops the same picture much narrower, so it gets a flatter bottom-up-only fade instead (its own media query in the same class) rather than the diagonal, which would barely register on a narrow column. The three-way fallback (real desktop photo → phone-only photo with the drawn `AtriumScene` on wide screens → drawn scene everywhere) is unchanged, just full-bleed now instead of masked to the right two-thirds.

The "Watch Our Story" outline button gets an explicit cream border/text override (`Button`'s `outline` variant defaults to copper-on-cream, meant for sitting on the plain page) since it now sits on a photo instead.

**A real layout bug caught by measuring, not by eye**: with the hero's mobile content now three lines taller (title + subcopy + two buttons all inside the photo instead of only the title/subcopy, with the buttons previously below on the plain page), the floating search card's fixed `-mt-16` pull-up started overlapping the bottom ~24px of the "Watch Our Story" button on phones (and ~8px at the `sm` breakpoint) — the button was covered mid-word. Fixed by giving the hero more bottom padding on both breakpoints (`pb-24`/`sm:pb-28`, up from `pb-10`/`sm:pb-14`) so the pull-up only ever eats into empty photo, never a control. Caught by comparing `getBoundingClientRect()` of the button row against the search card, not by trusting a screenshot alone — a lesson from the last slice repeated here on purpose.

## The announcement strip and header: one panel, not two bars (`app/globals.css`, `AnnouncementBar.tsx`, `Navbar.tsx`)

The flush-bar work (the same day, previous slice) already removed the *gap* between the two, but the strip was still a flat `bg-brand-primary` sitting directly against the header's own diagonal gradient (lighter at the top-left, darkening toward the bottom-right) — which starts noticeably *lighter* than flat primary, so there was a visible brightness step right at the seam. Two independently-sized boxes each computing their own gradient from 0–100% of their own height were never going to line up reliably at the boundary between them, gradient tuning would only ever get close. Instead: a new token, `--gp-bar-top` (`color-mix(in srgb, var(--gp-primary) 92%, white 8%)` — the exact shade the header's gradient already started at), used as the announcement strip's flat fill (`.gp-bar-top`) *and* as the header gradient's own starting stop (`.gp-bar-gradient`, extracted out of `.gp-header-inner`'s own rule so both components share the literal same class). Because both sides evaluate to the identical colour by construction, not by visual tuning, the seam can't show a mismatch regardless of either box's height.
