# Stage 2 — Auth

**Completed:** 2026-09-18 (email/password + role enforcement fully done and verified; Google OAuth
code-complete pending credentials; phone OTP deliberately deferred — see below)

## What was built

- `lib/auth/session.ts` — `getServerUser()` and `requireRole()`, always re-reading role from
  `public.users` rather than trusting anything client-supplied.
- `lib/auth/actions.ts` — Server Actions for sign-up, sign-in, sign-out, Google OAuth kickoff, and
  password reset request/update, each rate-limited via `lib/auth/rate-limit.ts`.
- `lib/auth/rate-limit.ts` — Upstash-backed, but fails open (no-ops) if Upstash isn't configured, so a
  fresh clone without `.env.local` filled in doesn't get rate-limited into uselessness.
- `proxy.ts` — Next 16's renamed `middleware.ts`. Optimistic redirect layer only; the real enforcement is
  `requireRole()` inside each protected page/route.
- Pages: `/sign-up`, `/sign-in`, `/reset-password`, `/update-password`, `/auth/callback` (route handler).
- Minimal protected stubs (`/account`, `/diary`, `/vendor/dashboard`, `/vendor/register` (public),
  `/admin/dashboard`) — these exist to prove the auth/role plumbing, not as real feature pages; later
  stages replace their contents without touching the routing/protection logic.
- `components/auth/{GoogleButton,SubmitButton}.tsx`, `components/layout/AccountMenu.tsx` (role-aware
  dropdown replacing the static "Sign In" button once a session exists).
- `app/error.tsx` — a branded fallback error boundary.

## A mid-session scope change: the cost constraint

Partway through this session, the client set a hard annual budget ceiling (~₹40–50k/yr for APIs, ~₹60–70k
including Vercel hosting + domain). This wasn't a suggestion — it eliminated Remove.bg and Railway from
the project entirely and reshaped how several other integrations get used. Full detail, including the
actual math behind why this is achievable, lives in `CLAUDE.md`'s "Cost constraint" section — read that
before adding *any* new paid dependency to this project, not just during Stage 2. The short version:

- Remove.bg: cut. No AI background removal/replacement. Vendors upload finished photos.
- Railway: cut. Stage 9's diary-reminder cron becomes a Vercel Cron Job (already confirmed technically
  sufficient — Pro plan supports up to 100 cron jobs/project with a configurable 300s timeout).
- MSG91 phone OTP: built behind a `PHONE_OTP_ENABLED` flag (default off), not ripped out — a genuine
  secondary-verification feature the client can turn on later without a redeploy needing code changes.
- Shiprocket: Lite/pay-as-you-go plan, not a fixed-fee tier, until volume actually justifies it.
- OneSignal: free tier is expected to be enough specifically because this product has no native mobile
  app (the SRS's own stated scope) — its new MAU cap only applies to mobile push.
- Resend and Cloudinary are the two real risks — both flagged explicitly rather than silently assumed to
  fit the budget forever.

## Two real bugs found by hand-testing in the browser (neither caught by `npm run build`)

1. **Sign-out did nothing, silently.** A `<button type="submit">` nested inside a Radix
   `DropdownMenu.Item` never triggered its wrapping `<form>`'s submission — Radix's own click handling
   (menu-item selection/close) intercepts the click first. Confirmed by checking `document.cookie` after
   clicking "Sign Out" and finding the session cookie still present, twice, with two different click
   approaches, before finding the actual cause. Fixed by calling `signOutAction()` directly from the
   item's `onSelect` handler instead of relying on native form submission. **Lesson for later
   stages**: any future button-inside-a-menu-item pattern (admin bulk actions, vendor quick actions, etc.)
   should use `onSelect` + a direct server-action call, not a nested form.
2. **Sign-up looked broken but wasn't** — Supabase's default/shared SMTP has a strict built-in
   rate limit on outgoing auth emails, and this session's repeated test sign-ups tripped it
   (`429 over_email_send_rate_limit`). Diagnosed by temporarily adding `console.error` logging around the
   `signUp()` call and reading the dev server's logs, then removed once confirmed. This is a real
   production concern, not a code bug: **custom SMTP must be configured in Supabase Auth settings before
   go-live**, or real users will hit the same limit. Resend (already planned for Stage 9's transactional
   email) is the natural choice — worth considering wiring in earlier than Stage 9 specifically to fix
   this during ongoing development, developer's call.

## Verification methodology (why this stage's "done when" is actually met, not just plausible)

Every claim below was checked live in the browser, not inferred from reading the code:
- Created 3 confirmed accounts directly via the Supabase admin API (bypassing the email-confirmation
  requirement, which would otherwise be blocked by the same rate limit) — `test-customer@giftping.test`,
  `test-vendor@giftping.test`, `test-admin@giftping.test`, password `TestPass123!` for all three. Left in
  the database deliberately, for reuse in later stages' manual testing (cart, wishlist, vendor portal,
  admin panel). Not real user data; delete before go-live.
- Signed in as each role and confirmed: customer blocked from `/admin/dashboard` and `/vendor/dashboard`
  (redirected home by `proxy.ts`); vendor reaches `/vendor/dashboard` but is blocked from
  `/admin/dashboard`; admin reaches both.
- Confirmed unauthenticated access to `/account` redirects to `/sign-in?redirectTo=%2Faccount` and, after
  signing in, lands back on `/account` — the full round trip, not just the initial redirect.
- Confirmed an already-authenticated session hitting `/sign-in` or `/sign-up` bounces to `/`.
- **Specifically isolated `requireRole()` from `proxy.ts`** to prove server-side enforcement is real and
  not just decorative: temporarily disabled proxy's admin-path check with a literal `if (false && ...)`,
  confirmed a customer session hitting `/admin/dashboard` still hard-failed (visible as a thrown
  `AuthError("FORBIDDEN", ...)` from `lib/auth/session.ts:57`, not a silently-rendered page), then
  restored the check. This directly satisfies the plan's stated "server-rejected, not just UI-redirected"
  requirement for this stage — the two layers were shown to be independent, not one relying on the other.
- Full sign-up flow tested with real field values (verified via direct DOM inspection before submission,
  since a viewport/coordinate mismatch in the browser tool caused two earlier attempts to submit with
  empty fields — worth knowing about if browser-based testing produces confusing "generic error" results
  again: verify field values directly rather than trusting that a coordinate click landed correctly).

## What's genuinely not done yet

- **Google OAuth**: code is complete (`signInWithGoogleAction`, `/auth/callback` handles the code
  exchange for both OAuth and email confirmation) but has never actually been exercised, because it needs
  a Google Cloud OAuth client that doesn't exist yet. Not a risk — it's a small, well-isolated piece — but
  don't report it as verified.
- **MSG91 phone OTP**: zero implementation, deliberately. Only the `PHONE_OTP_ENABLED` env flag exists as
  a placeholder. Build this only when/if the client decides to turn it on.

## How to verify this stage

- `npm run build` — zero errors.
- Sign in as each of the three test accounts above and repeat the role-matrix checks described above.
- `npm run dev`, sign in, click the account menu, click "Sign Out" — confirm it actually clears the
  session (check `document.cookie` for `auth-token`, or that the nav reverts to showing "Sign In").
